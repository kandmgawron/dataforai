Choosing a Vector Store

Where do 22,000 product vectors live?

From RAG Prototype to Production: AI Data Architecture on AWS
You know what embeddings are. You know we're using Titan Embed v2 at 1024 dimensions. The question now: where do you store them so you can search by meaning? AWS gives you several options. This video covers what they are, when to use each, and why Meridian uses two of them.
The landscape

Vector stores on AWS

OpenSearch Serverless

Purpose-built for search. Combines BM25 keyword matching with vector similarity in a single hybrid query. NextGen collections scale to zero when idle. Managed infrastructure, no patching or capacity planning.

Best for: product discovery, catalogue search, user-facing queries

Aurora pgvector

Add vector search to your existing PostgreSQL database. No new service, no new billing dimension. Vectors live alongside structured data (price, stock, category). ACID transactions mean embeddings stay consistent with product updates.

Best for: similar-product lookups, small-medium catalogues, unified data model

S3 Vectors

Store and query vectors directly in S3. No infrastructure to provision. Pay only when you query. Latency is higher (not real-time), but cost approaches zero for infrequent use.

Best for: batch analytics, offline recommendations, archival similarity search

Bedrock Knowledge Bases

Fully managed end-to-end: point it at a document bucket, it handles chunking, embedding generation, storage, and retrieval. Least code, least control. Cannot customise chunking or scoring.

Best for: policy documents, FAQs, internal knowledge where defaults are acceptable

Four options. Each has a sweet spot. OpenSearch Serverless is purpose-built for search. It does BM25 keyword AND vector search in a single query. The NextGen collection type scales to zero when idle, so you're not paying when nobody's searching. For Meridian, this is the primary search engine. pgvector is an extension you add to PostgreSQL. Aurora already has it enabled. You're adding a column of vectors to your existing products table. No new service, no new network hop. The trade-off: it doesn't do hybrid search natively, and at very large scale (millions of vectors) it's slower than a dedicated vector database. S3 Vectors is new. You store vectors as objects in S3 and query them with a similarity API. Pay per query, no infrastructure. Good for batch analytics or infrequent searches. Not suitable for real-time search at the latencies Meridian needs. Bedrock Knowledge Bases is the most managed option. You point it at a document bucket, it handles chunking, embedding, storage, and retrieval. Least control but fastest to set up. Good for policy documents where you don't need custom chunking strategies.

This table is the decision framework. Walk through each row. Real-time search: if you need sub-100ms responses for user-facing search, S3 Vectors is out. The rest all work. Hybrid search: only OpenSearch does it natively in a single query. With pgvector you'd need to run two queries and combine scores yourself. That's doable but adds complexity. Scale to zero: OpenSearch NextGen and Aurora auto-pause both do this. Important for a course lab where you tear down nightly. Existing PostgreSQL: if you already have Aurora (Meridian does), pgvector adds vector search with zero new services. No new billing, no new IAM policies, no new VPC configuration. Operational overhead: Bedrock KB and S3 Vectors are both zero-ops. OpenSearch is low (managed service). pgvector is lowest because it's just your existing database. Scale: pgvector works well up to about 5 million vectors on Aurora. Beyond that, you hit memory and index rebuild time issues. OpenSearch and S3 Vectors handle billions.

What drives cost
  • Storage — bytes per vector × number of vectors
  • Compute — OCUs (OpenSearch) vs ACUs (Aurora) vs per-query (S3)
  • Queries — OpenSearch charges per OCU-hour, pgvector uses existing capacity
  • Ingestion — one-time Bedrock cost to generate embeddings (~£0.45 for 22k products)
Cost is where the decision gets real. At Meridian's scale of 22,000 products, everything is essentially free. pgvector adds a column to an existing table — zero marginal cost. OpenSearch NextGen scales to zero. S3 Vectors is pennies. The differences emerge at scale. At 500k vectors (if Meridian grows or you index reviews too), OpenSearch costs £15-25/month for the OCU hours during active search. pgvector is still cheap because it's sharing Aurora capacity you're already paying for. S3 Vectors remains the cheapest but can't do real-time search. At 10M vectors, the economics shift significantly. pgvector needs a larger Aurora instance for the indexes to fit in memory. OpenSearch is purpose-built for this scale. S3 Vectors is dirt cheap but query-time-limited. The one-time cost to generate all 22k embeddings with Titan Embed v2: about £0.45.
Meridian's architecture

Why we use both

OpenSearch Serverless
  • Primary search engine for Ridge Assist
  • BM25 + vector hybrid queries
  • Handles product discovery, browsing, filtering
  • Scale-to-zero between sessions
Aurora pgvector
  • Product detail source of truth
  • Embedding stored alongside structured data
  • Used for: 'find similar products' on detail page
  • Zero new services, zero new cost
Using both isn't over-engineering. They serve different access patterns. OpenSearch finds products. Aurora knows everything about them.
Meridian uses both. This isn't redundancy, it's different access patterns. OpenSearch is the search engine. When a customer types 'warm jacket for Scottish winter', OpenSearch handles that query. It combines BM25 keyword matching with vector similarity in a single request. It's optimised for discovery: fast, ranked, filterable. Aurora pgvector stores the embedding alongside the product record. When you're on a product detail page and want 'similar products', that's a pgvector query — find the 5 nearest vectors to this product's vector. It's a simple, cheap query against your existing database. The intentional drift we built into the demo (250 products only in one store, 250 only in the other) shows why having both matters and why consistency between them is a real engineering problem. That's what zero-ETL solves later in the course.

Time to switch to the notebook. We'll generate embeddings for a small sample of products, store them in both vector stores, and run the same natural language query against each. The point isn't which one is 'better' — it's seeing how the same vectors produce different results depending on the search algorithm. OpenSearch's hybrid scoring finds products that match both keywords AND meaning. pgvector's pure cosine similarity finds the semantically closest matches regardless of exact term overlap. Both are useful. Different tools for different jobs.
What we learned from the demo

Real-world observations

Results: "lightweight tent for summer festivals"
  • BM25 matched keywords: "Festival Hat", "Summer Liner", "Lightweight Tent" — only 1 of 5 was actually a tent
  • pgvector found tents by meaning: Compact Tent, 2 Tent, 3 Tent — understood the intent
  • OpenSearch knn also found tents: all 5 results were tents, different scoring order
Architecture observations
  • pgvector: instant writes — UPDATE a column, query immediately
  • OpenSearch: plan upfront — knn must be enabled at index creation
  • ANN takes time — had to wait for index structures to build
  • Drift is real — Aurora-only products failed in OpenSearch
BM25 found hats and liners because they contained "summer" or "festival". Vector search understood you wanted a tent. That's the difference between matching words and understanding meaning.
The results speak for themselves. When you search 'lightweight tent for summer festivals', BM25 fixates on the words 'summer', 'lightweight', and 'festival'. It returns a Festival Hat, Summer Liners, and only one actual tent. It matched keywords, not intent. Both vector approaches understood you wanted a tent. pgvector returned 4 out of 5 tents. OpenSearch knn returned 5 out of 5 tents. They understood the meaning of the query even though the product names don't contain the word 'festival'. The latency difference is also telling: BM25 at 613ms (cold OpenSearch), pgvector at 403ms, knn at 353ms. All acceptable for user-facing search, but the vector approaches were actually faster here because they're doing a simpler operation (nearest-neighbour lookup vs full-text scoring across 22k documents). On the architecture side: pgvector writes were instant. OpenSearch needed us to create a dedicated index with knn enabled upfront, then wait for the ANN structures to build after ingestion. And we hit the drift problem: 2 products existed in Aurora but not in the demo index. In production, you solve this with a proper ingestion pipeline that writes to both stores atomically.
